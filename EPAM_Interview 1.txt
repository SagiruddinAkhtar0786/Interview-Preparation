Collection Framework is a combination of classes and interface, which is used to store and manipulate the data in the form of objects.

While a Map is not a true collection in the sense that it does not implement the Collection interface, it is considered part of the Collections Framework in Java. This is because it provides a way to handle collections of data (in this case, key-value pairs) in a unified way. Examples include HashMap, TreeMap, LinkedHashMap, etc.

Before Java 8: In HashMap, when collisions occurred (i.e., multiple elements hashed to the same bucket), the elements were stored in a linked list.
Java 8 and After: If the number of elements in a bucket exceeds a certain threshold (default is 8), the linked list is replaced with a balanced tree (a Red-Black Tree). This improves performance for lookups, insertions, and deletions in buckets with many entries.
Tree-based Buckets: The switch from linked lists to trees helps in reducing the time complexity from O(n) to O(logn) in buckets with many collisions.

diff b/w put and post
-------------------------
PUT Method
----------
Purpose: The PUT method is used to update or create a resource at a specific URL. It is idempotent, meaning that multiple identical requests should have the same effect as a single request.
Usage: Typically used when the client wants to replace the resource at a specified URL with the new data provided in the request.
Idempotent: Yes, calling PUT multiple times will produce the same result as calling it once.
Cacheable: No, by default.
Request Body: Contains the data to be updated or created at the specified URL.
Response: Generally returns a 200 OK status if the resource was updated successfully, or 201 Created if a new resource was created.

POST Method
--------------
Purpose: The POST method is used to create a new resource or submit data to a server. It is not idempotent, meaning that multiple identical requests can result in different effects.
Usage: Typically used when the client wants to send data to the server to create a new resource, submit a form, or trigger some action.
Idempotent: No, calling POST multiple times may produce different results.
Cacheable: No, by default.
Request Body: Contains the data to be processed or used to create a new resource.
Response: Generally returns a 201 Created status if a new resource was created, or a 200 OK status for other successful operations.

PATCH Method
-------------
Purpose: The PATCH method is used to apply partial updates to a resource. It is meant to update only specific fields of the resource rather than replacing the entire resource.
Behavior: PATCH is not necessarily idempotent. The same PATCH request may not always have the same effect, depending on how it is implemented on the server.
Request Body: Contains a set of changes to be applied to the resource. The format of the request body can vary (e.g., JSON Patch, XML Patch).
Use Case: Use PATCH when you need to update only certain fields of a resource without modifying the entire resource.
Return a 404 Not Found Error: This is the most typical and standard behavior. If the resource does not exist, the server responds with a 404 Not Found status code, indicating that the resource could not be found.

----------
Definition: A stateless system does not retain any information about the interactions or transactions between requests. Each request from the client to the server is treated as an independent transaction, unrelated to any previous requests.

1, why you have functional interfaces in java when you can declare an abstract class in interface itself
----------------------------------------------------------------------------------------------------------
1. Simplicity and Focus on Single Responsibility:
----------------------------------------------------
Functional Interface: A functional interface is an interface with a single abstract method (SAM). This constraint enforces that the interface is intended for a single action or behavior. It’s a clear, focused contract that says, "I do one thing."

Regular Interface: A regular interface can have multiple abstract methods. This allows it to define a broader range of behaviors, which can be useful for complex types but can also make the interface less focused.


Functional interfaces are a key part of Java's support for lambda expressions, introduced in Java 8. Lambda expressions allow you to write more concise and readable code, especially for operations like filtering, mapping, and reducing collections.

If a functional interface had more than one abstract method, it wouldn't be clear which method the lambda expression is intended to implement.

Method references are another way to create instances of functional interfaces. Like lambda expressions, method references need a clear target, which is possible only when there is a single abstract method.

The single abstract method constraint helps the Java compiler perform type inference more effectively when using lambda expressions and method references, making the code more concise and reducing boilerplate.

Functional Programming Paradigm:
--------------------------------------
Functional Interface: They are integral to Java’s functional programming features, such as the Stream API and the Optional class. These features rely heavily on functional interfaces to enable operations like filtering, mapping, and reducing collections in a more declarative manner.
Regular Interface: While regular interfaces can be used in functional programming, they are less suited for it when they define multiple methods, as it complicates the use of lambdas and method references.

Enhanced Code Readability and Maintenance:
------------------------------------------------
Functional Interface: Using a functional interface makes it immediately clear that the implementing class or lambda expression is providing a specific piece of functionality. This can make code easier to understand and maintain.
Regular Interface: With multiple methods, a regular interface can be harder to grasp quickly, especially if the methods serve different purposes.


Non-functional interfaces can have multiple abstract methods, and they are used in different contexts where multiple related functionalities need to be defined.


In such cases, using anonymous classes is more appropriate as they can implement multiple methods, but they lack the conciseness and expressiveness provided by functional interfaces with lambda expressions.

In conclusion, the single abstract method requirement for functional interfaces is essential to their role in enabling lambda expressions and method references, fostering a clear, concise, and functional programming style within Java.

10,Spring boot layers ( presentation , business , persistence , database)
-------------------------------------------------------------------------------
Spring Boot follows a layered architecture in which each layer communicates with the other layer directly in a hierarchical structure. There are 4 layers in Spring Boot as follows:

Presentation Layer
Business Layer
Persistence Layer
Database Layer

1. Presentation Layer
This layer handles all the HTTP requests made by clients, then it translates the JSON parameter to object and also authenticates the request, and transfer it to the business layer. In short, it only consists of the frontend part or we can say the view part.

2. Business Layer
This is also known as the Service layer which handles all the business logic of an application. It consists of service classes and uses services provided by the data access layers. It also performs authorization and validation.

3. Persistence Layer
It contains all the storage logic which are required and translates the business objects to database rows.

4. Database Layer
In this layer, all the CRUD (create, read update, delete) operations are performed.

29,Primary key
------------------
1. Primary Key

Definition: A primary key is a column (or a set of columns) that uniquely identifies each row in a table. It ensures that each row is unique and not null.

Uniqueness: Each value in a primary key column must be unique across the table.
Non-nullability: A primary key column cannot contain NULL values.

CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY,
    FirstName VARCHAR(50),
    LastName VARCHAR(50)
);


30,Composite key
----------------
Definition: A composite key is a primary key that consists of two or more columns used together to uniquely identify a row. This is used when a single column is not sufficient to uniquely identify a row.

Uniqueness: The combination of values across the specified columns must be unique.
Non-nullability: None of the columns involved in the composite key can have NULL values.

CREATE TABLE CourseEnrollments (
    StudentID INT,
    CourseID INT,
    EnrollmentDate DATE,
    PRIMARY KEY (StudentID, CourseID)
);

Foreign key
--------------
Definition: A foreign key is a column (or a set of columns) in a table that provides a link between data in two tables. It references the primary key of another table, establishing a relationship between the two tables.

Referential Integrity: Ensures that the value in the foreign key column matches a value in the primary key column of the referenced table.


31,Unique key constraints
-----------------------------
Definition: A unique key constraint ensures that all values in a column (or a set of columns) are unique across the table, but unlike the primary key, it allows for one NULL value (or more, depending on the database system).

Uniqueness: Ensures that no two rows have the same value in the unique key column(s).
Nullability: Depending on the database system, unique keys can allow NULL values.

2. LEFT JOIN (or LEFT OUTER JOIN)
---------------------------------
Definition: The LEFT JOIN keyword returns all records from the left table (table A) and the matched records from the right table (table B). The result is NULL from the right side if there is no match.

SELECT Employees.EmployeeID, Employees.FirstName, Employees.LastName, Departments.DepartmentName
FROM Employees
LEFT JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;

if their is no match department it will return null


3. RIGHT JOIN (or RIGHT OUTER JOIN)
--------------------------------------
Definition: The RIGHT JOIN keyword returns all records from the right table (table B) and the matched records from the left table (table A). The result is NULL from the left side when there is no match

SELECT Employees.EmployeeID, Employees.FirstName, Employees.LastName, Departments.DepartmentName
FROM Employees
RIGHT JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;

In this example, all departments will be listed, and if a department does not have any employees, EmployeeID, FirstName, and LastName will be NULL.

4. FULL JOIN (or FULL OUTER JOIN)
------------------------------------
Definition: The FULL JOIN keyword returns all records when there is a match in either left (table A) or right (table B) table records. It returns NULL for non-matching rows from either table.

SELECT Employees.EmployeeID, Employees.FirstName, Employees.LastName, Departments.DepartmentName
FROM Employees
FULL JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;

Concurrent HashMap
--------------------
=> ConcurrentHashMap is a thread-safe version of HashMap in Java, designed to allow concurrent access to the map by multiple threads without requiring explicit synchronization.
=> It was introduced in Java 5 as part of the java.util.concurrent package and has undergone significant improvements, especially in Java 8.

Thread Safety Without Locking the Entire Map
----------------------------------------------
ConcurrentHashMap allows concurrent read and write operations. It does this by partitioning the map into segments or buckets, each of which can be locked independently. This means that multiple threads can modify different segments of the map simultaneously.

No null key and values
-----------------------
Unlike HashMap, ConcurrentHashMap does not allow null keys or null values. This is to avoid ambiguities in concurrent programming,

Perfomance
----------
Java 8 introduced significant changes to ConcurrentHashMap. The most notable is the replacement of the segment-based locking mechanism with a finer-grained locking mechanism that reduces contention and improves scalability.

Parallel Operations: Java 8 introduced methods like forEach, search, and reduce for performing parallel operations on the map.
-------------------

Before Java 8: It used a method where the map was divided into sections called "segments." Each segment could only be accessed by one thread at a time, which sometimes led to delays because only a few threads could work on the map simultaneously.

n Java 8: Instead of locking large sections, it now locks much smaller parts (called "bins") only when necessary. It also uses a technique called optimistic locking, where it assumes everything will work fine (using a quick check) and only locks if it notices a problem. This allows more threads to work on the map at the same time without getting in each other's way, making it faster and more scalable.

They do not throw ConcurrentModificationException if the map is modified after the iterator is created.

he use of lock-free reads and fine-grained locking ensures that it can handle a large number of threads efficiently.

Atomic variables
-------------------
Atomic variables in Java are a type of variable provided by the java.util.concurrent.atomic package that supports lock-free, thread-safe operations on single variables. They are designed to be used in multi-threaded environments where you need to ensure that updates to a variable are done atomically (without interruption).

Key Features of Atomic Variables
---------------------------------
Atomic Operations
-----------------
Atomic variables ensure that operations like read, write, and update are performed atomically, meaning they cannot be interrupted by other threads. This is crucial in multi-threaded applications to avoid issues like race conditions.

No Need for Synchronization
-----------------------------
Because atomic variables handle thread safety internally, there's no need to use synchronized blocks or methods, which can simplify code and improve performance by reducing lock contention.

CAS (Compare-And-Swap)
------------------------
Many atomic operations are implemented using a technique called Compare-And-Swap (CAS). CAS checks if the current value is what you expect it to be, and if so, it changes the value to a new one in a single atomic step. If not, it retries until successful.

Binary Search

SingleTon class
----------------
=> A singleton class in Java is a class that is designed to allow only one instance of itself to be created throughout the application's lifecycle. It ensures that a single, globally accessible instance is provided, and no more than one instance can exist.

Reflection
-------------
=> Reflection can be used to access the private constructor and create a new instance, bypassing the singleton pattern.

Prevention =>  To prevent this, you can modify the constructor to throw an exception if an instance already exists.

Serialization and deserialization
----------------------------------
=> When a singleton class is serialized and then deserialized, a new instance of the class is created.

Prevention => To prevent this, you can override the readResolve() method to return the existing singleton instance.

Cloning
-------
=> If the singleton class implements Cloneable, it's possible to create a clone of the singleton instance.

=> To prevent this, override the clone() method to throw an exception.

While the singleton pattern is a powerful design pattern, it's not foolproof. Reflection, serialization/deserialization, cloning, and class loader issues are ways the pattern can be broken. However, by carefully implementing additional safeguards, you can minimize the risk of these issues in your applications.

Static methods
--------------

Static methods inside interfaces belong to the interface itself and not to the objects of the class that implements the interface.
Cannot be overrident in implementation classes

multiple inheritance concept in default methods
------------------------------------------------
Java uses the following rules to resolve conflicts when a class implements multiple interfaces with the same default methods.

Classes win 
============
interface AB(){
	default void print(){
		System.out.println("printing from interface A");
	}
}

class A(){
	default void print(){
		System.out.println("printing from interface A");
	}
}

class B extends A implements AB{
	print(); //print class A method not interface method
}

Most specific Interface win
----------------------------
interface AB(){
	default void print(){
		System.out.println("printing from interface A");
	}
}

interface CD(){
	default void print(){
		System.out.println("printing from interface A");
	}
}

class A implements AB,CD{
	@Override
	public void print(){
		System.out.println("printing from class A");
		AB.super.print(); //print from interface AB
	}
}

Thread Group
-------------
Java provides a convenient way to group multiple threads in a single object. In such a way, we can suspend, resume or interrupt a group of threads by a single method call.

Java thread group is implemented by java.lang.ThreadGroup class.

A ThreadGroup represents a set of threads. A thread group can also include the other thread group. The thread group creates a tree in which every thread group except the initial thread group has a parent.

A thread is allowed to access information about its own thread group, but it cannot access the information about its thread group's parent thread group or any other thread groups.

1)	ThreadGroup(String name) => creates a thread group with given name.
2)	ThreadGroup(ThreadGroup parent, String name) => creates a thread group with a given parent group and name.


Obsolescence: The ThreadGroup API is considered obsolete, as the java.util.concurrent package provides more robust and flexible ways to manage threads.
Limitations: Many methods in ThreadGroup are deprecated, and it doesn’t offer sufficient control over individual threads. It's generally better to use thread pools or other concurrency utilities provided in the java.util.concurrent package for managing groups of threads in modern Java applications.

Mutable / Immutable objects
------------------------------
In Java, objects can be classified as either mutable or immutable based on whether or not their state (i.e., their fields' values) can be changed after they are created.

Mutable Objects
--------------
A mutable object is an object whose state can be changed after it is created. This means that you can modify the values of the object's fields or properties after the object has been instantiated.

Characteristics of Mutable Objects:
------------------------------------
Fields can be modified: The fields (or properties) of a mutable object can be altered after the object is created.
Methods can modify state: The object's methods can change the internal state of the object.
Example classes: Common examples of mutable classes in Java include StringBuilder, ArrayList, HashMap, and any custom class where you have setter methods or methods that alter the internal fields.

Immutable objects
------------------
An immutable object is an object whose state cannot be changed after it is created. Once an immutable object is instantiated, it cannot be altered, and any modification results in the creation of a new object.

Characteristics of Immutable Objects:
-------------------------------------
Fields cannot be modified: All fields of an immutable object are typically declared as final (or not modifiable in any way).
No setter methods: Immutable classes usually do not provide setter methods or any method that can alter the object's state.
Thread safety: Immutable objects are inherently thread-safe because their state cannot change after they are created.
Example classes: Common examples of immutable classes in Java include String, Integer, LocalDate, and custom classes where all fields are final and there are no setter methods.
